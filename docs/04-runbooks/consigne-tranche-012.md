## Exigences pour le contrat
1. **Aucun travail serveur nouveau** : les pages s'appuient sur les modules et routes existants (001 a 006, 009, 013). Aucune migration, aucun contrat d'API nouveau ou modifie (hors D-143), aucune fonction `SECURITY DEFINER`, aucun privilege. **Aucune dependance nouvelle** (D-137 point 2) : React, Next et `better-auth` suffisent. Si l'un de ces points ne tient pas, arrete-toi et dis pourquoi.
2. **Ecrans** (D-137 point 3), en francais, chemins a proposer : accueil (renvoi selon la session), connexion, inscription, mes organisations et creation, page d'organisation, page de collection, acceptation d'invitation (chemin `/invitations/accept` impose par le lien d'e-mail de 003). Dis pour chaque page : qui y accede, ce qu'elle lit, quelles actions elle offre, quelle route chaque formulaire appelle, et ce qui s'affiche pour chaque erreur du contrat (dont `409 FREE_TIER_QUOTA_EXCEEDED` et `409 COLLECTION_NAME_TAKEN`).
3. **Roles** : palier et formulaire d'invitation visibles par l'owner seul ; le member ne les voit pas et la page ne les lui envoie pas (ni dans le HTML, ni dans les donnees embarquees par Next). Le role vient du serveur, jamais d'un parametre de l'adresse.
4. **Isolation** : page d'une organisation dont on n'est pas membre, ou d'une collection d'une autre organisation -> page introuvable (`404`) **identique** a un identifiant inexistant ; aucune donnee d'autrui dans la reponse, y compris les donnees embarquees. Page privee sans session -> renvoi vers la connexion, sans aucune donnee.
5. **Affichage sur** (backlog, audit-005 INFO-2) : tout texte libre (nom d'organisation, de collection, titre, URL, adresse) passe par le rendu echappe de React, jamais `dangerouslySetInnerHTML` ; nom d'hote affiche a part, tire de `new URL(url).hostname` (punycode) ; liens externes avec `rel="noopener noreferrer"` et `target` explicite ; `href` seulement si le schema est `http:` ou `https:` (verifie de nouveau a l'affichage) ; aucune valeur libre dans un autre attribut. Preuve par test : des valeurs piegees (`<script>`, `"><img onerror=...>`, `javascript:` dans un titre, U+202E, U+200B) n'apparaissent **nulle part** non echappees dans la reponse complete, donnees embarquees comprises.
6. **Jeton d'invitation** : lu dans le fragment par le navigateur, envoye seulement dans le corps du `POST /api/invitations/accept` ; jamais dans une adresse (`?`, chemin, renvoi apres connexion), un journal, un stockage serveur. Dis comment l'invite sans session se connecte ou s'inscrit **sans perdre le jeton et sans le faire sortir du fragment**. P-4 reste ferme : aucune lecture d'invitation sans session.
7. **Formulaires** : dis comment ils sont proteges contre une soumission depuis un autre site (cookie de session de `better-auth`, type de contenu exige par les routes) et verifie-le. Messages d'erreur : les textes fixes des routes, jamais la valeur soumise.
8. **Preuves automatiques** (D-137 point 1) : tests qui lisent les pages rendues par le serveur de test existant (meme `globalSetup`), avec des comptes de test ; contenu attendu par role, ordre d'affichage (celui des lectures), points 3, 4, 5 et 6. Aucune comparaison permanente a `main` ; valeurs de test visiblement fausses.
9. **Visite guidee par l'humain** (D-137 point 1) : `docs/04-runbooks/recette-012.md`, liste a cocher (15 minutes environ) et prerequis exacts pour lancer l'application sur le poste. Etat connu du poste (backlog D-067) : `.env` non aligne sur `.env.example`, base de developpement non migree depuis 0016. Les prerequis renvoient a la procedure existante (`stripe-facturation-locale.md` § 1, etape 4), avec `env-check.ps1` ; **aucune valeur affichee, aucun fichier `.env*` lu par un agent**. Verifie ce que le mode developpement permet vraiment : aucun fournisseur d'e-mail (seul `APP_ENV=test` accepte la fausse messagerie) et Inngest. Ce qui n'est pas faisable sur le poste (recevoir l'e-mail d'invitation, sans doute) est prouve par les tests automatiques et **dit comme tel** dans la liste. **Aucun assouplissement des gardes d'environnement** (`EMAIL_CAPTURE_URL`, `STRIPE_API_BASE_URL`, `AUTH_RATE_LIMIT` restent reserves aux tests). La PR n'est fusionnee qu'apres la visite, resultat consigne par l'humain.
10. **Hors tranche explicite** (D-137 point 4) : changement de palier, retrait d'un membre, suppression d'une collection, organisation active en session, lecture d'invitation sans session, pagination, mise en page soignee.
