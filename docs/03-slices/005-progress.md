- Implementeur, migration : index `link_collection_recent_idx` declare `.desc().nullsFirst()` dans Drizzle. Raison : `.desc()` seul emet `DESC NULLS LAST`, different de l'ERD (`DESC`, soit `NULLS FIRST` par defaut) et du test d'AC12 ; colonnes `NOT NULL`, donc aucun effet sur le tri. Ecarte : corriger le SQL genere a la main (instantane `meta/` desaligne, la generation suivante produirait une difference).
- Implementeur, migration : nom du trigger `link_usage_on_insert`, comme la fonction (le contrat ne le nomme pas). Il s'execute apres les triggers internes de cle etrangere (`RI_ConstraintTrigger_*`, ordre alphabetique) : sans effet sur le resultat, toute erreur annule l'instruction entiere.
- Implementeur, migration : messages de `RAISE` sans identifiant d'organisation (ni pour `SG001`, exige, ni pour `P0001`). Ecarte : reprendre l'identifiant dans `P0001` comme `propagate_subscription_quota` (il remonterait dans les journaux du serveur sans necessite ; la route ne journalise que le code).
- Implementeur, migration : aucun garde `NULL` explicite sur `NEW.organization_id` avant `set_config` (regle n°3 de `drizzle-postgres.md`) : la colonne est `NOT NULL`, verifiee avant tout trigger `AFTER` ; un `NULL` ferait de toute facon toucher zero ligne, donc lever `P0001`. Garder `set_config` en premiere instruction, comme l'exige le contrat.
- Implementeur, logique metier : point de sauvegarde autour de l'`INSERT` (patron D-092/D-116), **mesure de proprete, non prouvee par un test** (reformule apres review-005 SUGGESTION 1) : un `SG001`/`40001` annule l'insertion seule et `withTenant` valide une transaction saine. Sans lui, le resultat observable serait le meme : Postgres repond a un `COMMIT` sur une transaction en echec par un `ROLLBACK`, sans erreur, et la route rendrait le meme `409`. Il ne devient utile que si du code venait un jour ecrire dans la transaction apres le refus. Ecarte : laisser `withTenant` annuler sur une exception typee (il faudrait modifier `db.ts`, hors perimetre, ou lever une exception pour une erreur metier, contraire a CLAUDE.md).
- Implementeur, logique metier : parametres de l'`INSERT ... SELECT` castes explicitement (`$1::uuid`, `$3::text`...) : `$1` apparait a la fois dans la liste de selection et dans le `WHERE`, le type ne doit pas dependre de l'inference.
- Implementeur, logique metier : message du `404 COLLECTION_NOT_FOUND` « Collection introuvable. » (le contrat ne le fixe pas ; meme forme que « Organisation introuvable. »).
- **Remplacee par D-125** (le refus est desormais dans `addLink.input.title`, la garde de la route est retiree, 7ebbc10). Texte d'origine conserve pour la trace — Implementeur, API, a faire valider (contract-guardian, humain) : un titre contenant U+0000 est refuse en `422` par un garde de la route, **apres** le contrat (`addLink.input.title` l'accepte). Raison : AC4 exige `422` et jamais `500` ; Postgres ne peut pas stocker U+0000 dans un `text` (`22021`), sans garde l'entree finit en `500`. Seul U+0000 est refuse (les autres caracteres de controle du titre sont stockables, rien ne les exige refuses). Ecartes : modifier `addLink.input.title` dans `links.ts` (changement de contrat publie, decision humaine, D-120 ne portait que sur l'URL) ; traduire `22021` en `422` apres l'appartenance (un non-membre recevrait `404` au lieu de `422`, contraire a l'ordre « validation avant appartenance », AC11). Si l'humain prefere inscrire la regle dans le contrat, le garde de la route devient redondant et se retire.
- Implementeur, API : textes fixes des `422` (non figes par les tests, D-124) : corps non JSON ou non objet, organisation, collection, URL (nomme la regle : http ou https en minuscules, nom d'hote, sans identifiants, espaces ni caracteres de controle, 8 a 2048), titre (1 a 200, bords exclus, sans caractere nul). Premier champ fautif dans l'ordre chemin (organisation, collection), `url`, `title`. Depuis D-125, le message du titre couvre aussi le refus de U+0000 porte par le contrat (texte inchange).
